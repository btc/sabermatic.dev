**Date**: 2026-04-03

**Purpose**: Complete frontend design for Drill's React SPA — all pages, components, interaction patterns, and visual system. Clean-room build using shadcn/ui, informed by the v0 prototype but not derived from it.

## 1. Product Personality

Warm, safe, restrained. Linear's confidence and precision without its coldness. The app speaks with clarity — no fluff, no exclamation marks, no "Great job!" when you scored a 2/5. It respects the user's intelligence. But underneath that crispness, it feels safe. This is a practice space. The user is here to get better, and the tool knows that.

**Communication voice:** direct, lowercase energy, no unnecessary words. "Your session is ready." not "Let's get started!" — "3 gaps identified" not "We found some areas for improvement!"

**Scores are growth data, not verdicts.** A 2/5 in scalability isn't a red failure badge — it's a clear signal of where to focus next. The UI presents gaps the same way it presents strengths: as information. The educator and coach exist because the product assumes you'll have gaps and has built the entire second half of the experience around closing them.

**Information density scales to context.** The interview page is focused and minimal — just you and the conversation. The results page is rich and detailed — scores, annotations, transcript. The dashboard gives you the full picture without making you hunt.

| Role | Size | Weight | Font |

### Button System

Consistent action placement across the entire app:

- **Left side**: back/exit/cancel — navigates away, escapes current context
- **Right side**: primary forward action — the thing the user is here to do
- **Center**: contextual information (timer, status)

Visual hierarchy:
- **Primary**: amber background, dark text. One per screen.
- **Secondary**: outlined, stone border. Supporting actions.
- **Ghost**: no border, text only. Navigation, muted actions (cancel, back).
- **Destructive**: red outlined or red ghost. Dangerous actions (delete account).

Inline error messages use warm orange text below the field, not aggressive red.

### Architectural Rules

- **`api/queries.ts`** is the single source of truth for all server data fetching. Every component that needs data uses a TanStack Query hook from here. No raw `fetch()` elsewhere.
- **`ws/`** is self-contained. Only the interview page touches WebSocket. `useInterview()` exposes the full interview state machine.
- **`audio/`** is self-contained. Recorder and player are independent. Recorder handles multi-segment capture + concatenation. Player handles TTS chunk queuing + sequential playback.
- **`components/ui/`** contains only shadcn/ui primitives. No custom component library alongside.
- **No frontend event tracking calls.** Backend logs user events as a side effect of handling API requests and WebSocket messages.

```

/sessions/:id                       Session detail — redirects to /overview
/sessions/:id/overview              Session detail — scores, strengths, gaps, advice
/sessions/:id/transcript            Session detail — annotated transcript
/sessions/:id/deep-dive             Session detail — educator content
/history                            History — all sessions, filters, trend chart
/settings                           Settings — profile, theme, linked accounts
/settings/billing                   Settings — plan, usage, Stripe portal
```

### Layouts

1. **AppLayout** — top bar with DRILL wordmark, Home + History nav links, avatar menu (right side). Wraps all pages except interview and auth.
2. **ImmersiveLayout** — no nav bar. Cancel (top-left) and End Session (top-right) with timer (center). Wraps only the interview page.
3. **Auth pages** — standalone. Centered card on plain warm-stone background. DRILL wordmark above.

### Navigation

Two nav links: **Home | History**. History is visually muted and disabled when the user has no sessions. It becomes active after the first session.

### Avatar Menu

Right side of the top bar. User avatar (or initials circle) that opens a dropdown:

- **Settings** → `/settings`
- **Theme** → light / dark / system toggle (quick access without navigating to settings)
- **Logout** → `POST /api/auth/logout`, redirect to `/login`

Keeps the top bar clean while making settings and logout always one click away.

### Auth Guard

`RequireAuth` wrapper component. TanStack Query fetches `GET /api/me` — if it returns 401, redirect to `/login?redirect=<current_path>`. After successful login, redirect back to the original path.

### Session Detail Tabs

`/sessions/:id` is a nested route layout. The parent layout fetches session + evaluation data once via TanStack Query. The three child tabs (overview, transcript, deep-dive) consume from the parent's query cache. No redundant fetches.

## 6. Pages

### 6.1 Home Page

**URL:** `/`

Progressive disclosure — the page grows with the user.

**New user (0 sessions):**
- No summary cards
- Welcome text: "Pick a question to start practicing. 30 minutes is a good first session."
- Question list showing seed questions

**Returning user (1-2 sessions):**
- Summary strip: latest overall score, sessions completed count
- Question list with per-question attempt count and best score on cards the user has attempted

**Active user (3+ reviewed sessions):**
- Summary strip: score trend sparkline (last N sessions), coach card with narrative excerpt
- Coach card with: narrative excerpt (first 2-3 sentences), weakest dimension badge, "Refresh" button (calls `POST /api/coach/analyze`). If coach is generating: "Analyzing your progress..." with breathing animation. If no analysis exists yet (3+ sessions but never triggered): "Get strategic coaching" button to trigger first analysis.
- Coach-suggested question highlighted in the list below ("Recommended by coach" marker)
- Full question list with filters

**Active session banner:** If the user has an active (in-progress) session, a banner appears above the question list: "You have a session in progress — [Question Title]" with a "Resume" button that navigates to `/sessions/:id/interview`. This also surfaces the concurrent session limit (free: 1, pro: 2) — if the user is at their concurrent limit, the Start buttons on question cards are disabled with a note: "End or resume your active session first."

**Question list:**
- Filterable by difficulty (dropdown) and tags (pill toggles)
- Filters reflected in URL params: `/?difficulty=hard&tags=caching` — shareable, bookmarkable
- Each question card shows:
  - Title
  - Difficulty badge (medium / hard)
  - Tag pills
  - Source indicator for non-seed questions: "Custom" or "Coach-generated" (with rationale tooltip for coach-generated)
  - Attempt count + best score (if attempted, subtle secondary text)
  - "Start" button → navigates to `/sessions/new?question=:id`

**Create custom question:** A "Create question" button above the question list opens a modal form with: title, prompt, difficulty (medium/hard), tags. Calls `POST /api/questions`. The new question appears in the list with a "Custom" badge.

### 6.2 Session Config Page

**URL:** `/sessions/new?question=:id`

**Layout:** App layout (top bar visible). Centered single-column card.

**Purpose:** Prepare the user mentally, configure the session, obtain microphone permission, provide the user gesture that satisfies browser autoplay policy.

**Content, top to bottom:**

1. **Question title + full prompt** — the interview-style vague problem statement. This is what the interviewer will open with.

2. **Configuration:**
   - Duration: preset buttons (15, 30, 45, 60 min) + custom input (1-180). Default: 30 min.
   - TTS toggle: "Interviewer voice responses" on/off. Default: on.
   - Coach briefing toggle: "Brief interviewer on your weak areas" on/off. Only shown if coach analysis exists for this user.

3. **Preparation tips** — short, static. Not patronizing:
   - "Think out loud — the interviewer evaluates your reasoning process"
   - "Start with requirements, not solutions"
   - "You can switch between voice and text at any time"
   - "Spacebar to record when not typing"

4. **Microphone encouragement + permission:** "For the best experience, use your voice. It's faster and more natural." Button to enable microphone via `getUserMedia()`. Checkmark once granted. If declined: "You can still use text input." (v2: mic test with live STT preview on this page.)

5. **Begin button** — primary amber, prominent. This click is the user gesture for browser autoplay policy. Creates session via `POST /api/sessions`, navigates to `/sessions/:id/interview`, WebSocket connects, interviewer TTS plays immediately.

**Edge cases:**
- Entitlement exceeded: Begin disabled. "You've used all 3 sessions this month." Upgrade link.
- Duration exceeds plan limit: custom input capped at plan max with clear label.
- No question param: redirect to home.

### 6.3 Interview Page

**URL:** `/sessions/:id/interview`

**Layout:** Immersive. No top bar. Full viewport.

**Header strip:**

```
┌──────────────────────────────────────────────────┐
│ ← Cancel              12:34           End Session │
│   (ghost)             timer             (primary) │
└──────────────────────────────────────────────────┘
```

- **Cancel** (top-left): ghost button. Confirms: "Leave this session? You can return to it later." Navigates to home. Session stays active. (See Section 6.1 for the active session resume banner.)
- **End Session** (top-right): primary amber. Confirms: "End this session? Your responses will be evaluated." Sends `end_session` via WebSocket, triggers evaluation.
- **Timer** (center): elapsed time. Warm amber text at the warning threshold (`clamp(2, 5, round(duration / 9))` minutes remaining). Soft red at overtime, shows "+0:32" format.
- **TTS indicator**: near timer. Subtle pulsing waveform or animated icon when interviewer audio is playing. Shows TTS on/off status when idle.

**Chat area:**

- Messages positioned near vertical center of viewport when conversation is short (first few exchanges sit at eye height, not pinned to the top or bottom of the screen). As conversation grows, the view scrolls naturally with the latest messages near center. The input area stays at the bottom; the chat content area above it is where centering applies.
- Interviewer messages: left-aligned. Clean text, no avatar.
- Candidate messages: right-aligned. Slightly warmer background tint to distinguish.
- Streaming: interviewer message builds token by token, left-aligned. The streaming text IS the indicator — no separate typing bubble.
- Loading shimmer: after candidate submits (voice or text), a subtle shimmer appears on the CANDIDATE'S side below their message. "Processing..." in muted text. Covers STT transcription and LLM thinking time. Moves to interviewer side only when tokens start streaming.

**Input area:**

Standard ChatGPT/Claude.ai style:
- Text field with placeholder "Type a response..." and send button on right.
- Microphone button integrated into the input area. Click to start recording, click to stop. Pulsing red ring while recording.
- **Spacebar push-to-talk:** when text field is NOT focused, spacebar starts recording. Release stops recording. Input area shows "Recording..." with waveform visualization.
- **Focus management:** clicking text field focuses it (spacebar types normally). Clicking outside or pressing Escape blurs it (spacebar records). Clear, predictable transitions.
- **Multi-segment recording:** record, stop, record again. Segments accumulate. Small segment indicators show clip count. "Submit" sends all segments concatenated. "Discard" clears.

**Reconnection:**

Subtle banner slides in at the top: "Reconnecting..." in amber. No panic. Disappears on reconnect. On `reconnect_please` from server (graceful deploy, 55-min preemptive reconnect), same brief banner while client reconnects without backoff.

### 6.4 Post-Interview: Waiting State

After End Session, the interview page transitions to a waiting view. Chat fades. A centered state appears:

- **Immediate session stats** (no LLM required): question title, duration, turn count. Honest, simple.
- **Cycling status messages** (~4 seconds each):
  - "Reviewing your requirements gathering..."
  - "Analyzing architecture decisions..."
  - "Assessing depth of technical discussion..."
  - "Evaluating scalability reasoning..."
  - "Reviewing communication clarity..."
- Subtle breathing animation. Not a progress bar — no percentage is known.
- If the user navigates away, that's fine. Session detail page checks evaluation status and shows waiting state if still pending, or results if ready.
- **Auto-navigation:** when evaluation completes, navigates to `/sessions/:id/overview`.
- **Direct navigation during evaluation:** if a user navigates to `/sessions/:id/overview` (or any session detail tab) before evaluation completes, the session detail page shows the same waiting state with cycling messages. The tab bar is visible but Overview content is replaced by the waiting view. Transcript tab is available (the transcript exists as soon as the session ends). Deep Dive tab shows its normal "Generate" prompt only after evaluation completes (educator requires evaluation results).

### 6.5 Session Detail: Evaluation Failed State

When a session has status `evaluation_failed`:
- **Overview tab:** shows an error message: "Evaluation could not be completed." with a "Retry evaluation" button that calls `POST /api/sessions/:id/evaluate`. No scores, strengths, gaps, or advice displayed.
- **Transcript tab:** fully available — the transcript exists regardless of evaluation status.
- **Deep Dive tab:** unavailable. Shows: "Deep analysis requires a completed evaluation. Retry the evaluation first."

### 6.6 Session Detail: Active Session

When a session has status `active` and the user navigates to `/sessions/:id` (e.g., from history):
- Redirect to `/sessions/:id/interview` to resume the interview. The WebSocket reconnects, `session_init` with `last_seq` triggers `reconnect_state`, and the conversation resumes where it left off.

### 6.7 Session Detail: Overview Tab

**URL:** `/sessions/:id/overview`

**Scores:** prominent, clean. Six scores (5 dimensions + overall). Each score 1-5 with label. Overall score larger/emphasized. Horizontal bars or similar visualization.

Score color coding:
- 1-2: stone-500 (muted) — not red, not punishing
- 3: amber (neutral, borderline)
- 4-5: green (strong)

**Strengths:** list of items with evidence quotes from the transcript. Green left-border accent. Each item has a "View in transcript" link that navigates to the Transcript tab scrolled to the relevant message.

**Gaps:** same format, orange left-border accent. Same "View in transcript" links.

**Advice:** narrative text, full content width. The evaluator's actionable guidance and metacognitive prompt. Natural reading position after strengths and gaps.

### 6.8 Session Detail: Transcript Tab

**URL:** `/sessions/:id/transcript`

Full conversation with annotations overlaid.

- Messages in chronological order. Interviewer left, candidate right — same layout as the interview page for familiarity.
- **Annotations:** colored callout cards attached to their message. A strength annotation on message #4 appears as a green-bordered card below that message. Gaps orange, missed opportunities purple, notes blue.
- **Annotation rail:** narrow column on the right edge with colored dots at vertical positions where annotations exist. Clicking a dot scrolls to that annotation. Instant visual map of where the interesting moments are.
- **Annotation summary bar** (top of tab): "14 annotations: 5 strengths, 6 gaps, 2 missed opportunities, 1 note" — each type is a toggleable filter. Click "gaps" to highlight only gap annotations (others dim but remain visible).
- **Jump navigation:** clicking a type in the summary bar scrolls to the first annotation of that type. Next/prev buttons to step through annotations sequentially.

### 6.9 Session Detail: Deep Dive Tab

## 7. Telemetry

### Distributed Tracing

`@opentelemetry/sdk-trace-web` with `@opentelemetry/instrumentation-fetch` for automatic `traceparent` header injection on all fetch calls. TanStack Query uses fetch, so all REST API calls are traced automatically.

For WebSocket (interview turns), the client creates a parent span and sends trace context in the WS message payload:

```typescript
// Client sends in end_turn message
{
  type: "end_turn",
  content: "...",
  input_method: "voice",
  trace_context: {
    trace_id: "abc123...",
    span_id: "def456..."
  }
}
```

The conductor extracts `trace_context` and uses it as the parent for all child spans: `turn.stt`, `turn.persist_input`, `turn.llm`, `turn.tts`, `turn.persist_response`. The client closes the parent span when `interviewer_done` arrives and TTS queue drains.

This gives one trace per turn in Cloud Trace: spacebar press → STT → LLM (time-to-first-token) → TTS → audio playback complete.

**TODO (backend):** Two changes required: (1) Update the backend spec's WebSocket message tables (Section 3) to include the optional `trace_context` field on `session_init` and `end_turn` messages. (2) Conductor must extract trace context from WS messages and propagate to child spans via OpenTelemetry context. Documented contract: `trace_context.trace_id` and `trace_context.span_id` fields on `end_turn` and `session_init` messages.

### User Event Logging

No frontend event tracking layer. The backend logs user events (`user_events` table) as a side effect of handling API requests and WebSocket messages. Session start is logged when `POST /api/sessions` is handled. Turn submission is logged when the conductor processes `end_turn`. No separate tracking calls from the frontend.

## 8. WebSocket Integration

The `ws/` module is self-contained. Only the interview page uses it.

### Protocol (matches backend spec Section 3)

**Client → Server:**

| Message | Payload |
|---|---|
| `session_init` | `{ last_seq: null \| N, trace_context?: { trace_id, span_id } }` |
| `end_turn` | `{ content, input_method: "text", trace_context?: {...} }` or `{ audio, input_method: "voice", trace_context?: {...} }` |
| `cancel_tts` | (none) |
| `end_session` | (none) |
| `ping` | (none) |

**Server → Client:**

| Message | Payload |
|---|---|
| `session_loaded` | `{ session_id, started_at, duration_minutes, tts_enabled }` |
| `reconnect_state` | `{ last_seq, messages: [...] }` |
| `interviewer_token` | `{ token }` |
| `interviewer_done` | `{ message_id }` |
| `tts_chunk` | `{ data, message_id, seq }` |
| `tts_done` | `{ message_id }` |
| `transcription_result` | `{ text, message_id }` |
| `timer_warning` | `{ minutes_remaining }` |
| `timer_overtime` | (none) |
| `session_ended` | `{ reason: "candidate" \| "interviewer" \| "timeout" }` |
| `reconnect_please` | (none) |
| `error` | `{ code, message }` |
| `pong` | (none) |

### Connection Management

`connection.ts` manages the WebSocket lifecycle:

- **Connect:** opens `WSS /api/sessions/:id/ws`, sends `session_init` with `last_seq` from local state.
- **Reconnect:** on unexpected close, exponential backoff (1s initial, 30s max, with jitter). On `reconnect_please`, reconnect immediately without backoff.
- **Preemptive reconnect:** for sessions > 55 min, the server sends `reconnect_please` at 55-min mark. Client reconnects seamlessly — brief "Reconnecting..." banner, no interruption.

### useInterview() Hook

The main interview state machine hook. Exposes:

- `state`: current conductor state (waiting, transcribing, interviewing, streaming, ended)
- `messages`: conversation messages array
- `isRecording`, `isStreaming`, `isTranscribing`: boolean flags for UI
- `sendText(content)`: send text turn
- `sendAudio(blob)`: send voice turn
- `endSession()`: send end_session
- `cancelTts()`: send cancel_tts
- `timerState`: elapsed time, warning/overtime status
- `ttsPlaying`: whether TTS audio is currently playing
- `connectionState`: connected/reconnecting/disconnected

## 9. Audio Integration

### Recorder (`audio/recorder.ts`)

Multi-segment audio recording:

- Uses `MediaRecorder` API. Preferred codec: WebM/Opus. On Safari, check `MediaRecorder.isTypeSupported('audio/webm;codecs=opus')` at init — if unsupported, fall back to `audio/mp4` (AAC). The backend STT service must accept both formats.
- Segments recorded independently, stored in memory as Blobs.
- On submit: segments concatenated into a single Blob, encoded to base64, sent via `end_turn` WS message.
- On discard: segments cleared from memory.
- Exposes: `start()`, `stop()`, `submit()`, `discard()`, `segments` (count), `isRecording`.

### Player (`audio/player.ts`)

TTS audio playback:

- Receives `tts_chunk` messages, queues them in order by sequence number.
- Plays chunks sequentially using Web Audio API. AudioContext must be created from a user gesture (the "Begin" button on session config satisfies this).
- On `tts_done`: drain remaining queue, signal completion.
- On `cancel_tts`: stop current playback, clear queue, send `cancel_tts` to server.
- Exposes: `enqueue(chunk)`, `cancel()`, `isPlaying`, `onComplete` callback.

### Spacebar Push-to-Talk

- When the text input field is NOT focused, `keydown` spacebar starts recording, `keyup` stops.
- When the text input IS focused, spacebar types normally.
- The input area shows a visual mode indicator during recording: waveform visualization + "Recording..." label.
- Focus management: clicking text field focuses it. Clicking outside or pressing Escape blurs it.

## 10. Progressive Disclosure

The app reveals itself as it becomes relevant. Sections and features appear when they have something meaningful to show.

| User state | Home page | Nav | Session detail |
|---|---|---|---|
| 0 sessions | Welcome text + question list | History disabled | N/A |
| 1-2 sessions | Score + session count strip, question list with attempt data | History enabled | Overview + Transcript tabs. Deep Dive tab present (educator available). |
| 3+ reviewed | Coach card + trend sparkline + highlighted suggestion, full question list | Full nav | All three tabs. Coach briefing toggle on config page. |

Blank states are designed experiences, not empty containers. They guide the user to the next action.

### Loading States

All pages use skeleton/shimmer placeholders for initial data loads via TanStack Query. The shimmer style matches the existing interview loading shimmer (warm stone tones, subtle animation). Skeletons mirror the final layout shape so the page doesn't jump when data arrives. TanStack Query's `staleTime` and background refetch mean subsequent visits show cached data immediately with a background refresh — no visible loading after the first visit.

## 11. Embedding in Go Binary

The Vite build outputs to `web/dist/`. The Go binary embeds this via `embed.FS`:

A dedicated `web.go` file at the project root handles embedding:

```go
// web.go (project root, next to web/ directory)
package drill

import "embed"

//go:embed web/dist
var WebFS embed.FS

// cmd/drill/main.go references drill.WebFS to serve the SPA.
// All non-API routes return web/dist/index.html for client-side routing.
// Static assets (JS, CSS, fonts) served directly from web/dist/assets/.
```

The Dockerfile gains a Node.js build stage:

```dockerfile
# Stage 1: Build frontend
FROM node:22-alpine AS frontend
WORKDIR /app/web
COPY web/package.json web/package-lock.json ./
RUN npm ci
COPY web/ .
RUN npm run build

# Stage 2: Build Go binary
FROM golang:1.24-alpine AS backend
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
COPY --from=frontend /app/web/dist ./web/dist
RUN go build -o drill ./cmd/drill

# Stage 3: Runtime
FROM gcr.io/distroless/static-debian12
COPY --from=backend /app/drill /drill
ENTRYPOINT ["/drill"]
```

The SPA handler serves `index.html` for all routes not matching `/api/*` or static asset patterns. React Router handles client-side routing from there.

Vite dev config proxies `/api/*` to the Go backend for local development:

```typescript
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        ws: true,  // Required for WebSocket upgrade on /api/sessions/:id/ws
      },
    },
  },
});
```
